# Publication protocol

## Prepare

1. Load the current user-edited draft and intended source; check recent platform posts and the stable publication key for duplicates.
2. Verify the signed-in account and actual composer capability. Users sign in themselves on official sites. Keep cookies, passwords, OTPs and OAuth secrets out of chat, files and content databases.
3. Bind the preview to platform, account, exact text, attachment identity, link, topic/audience settings, and immediate or scheduled delivery. Check media visually and verify the upload completed. A link preview is not an uploaded video.
4. Present the concrete preview. Obtain explicit approval for that version and destination. Existing explicit authorization covering the exact version/media/account/time can satisfy this; don't ask repeatedly without a change. If content, attachment, destination or time changes materially, renew approval.

## Execute

Use the host's supported connector or browser and its confirmation rules. One site's login does not grant an API permission or permission on another platform. New OAuth grants are completed through the provider's official flow. Never fabricate a background scheduler.

Send once. If the action times out or navigation is interrupted, classify the outcome as uncertain and inspect recent posts before trying again. For a thread with replies, record each successful URL and retry only the missing part with appropriate authorization.

## Reconcile

Only after a visible success and a verified detail page, record the permalink, platform ID if available, actual timestamp with timezone, attachment identity and approved version. A URL shortcode is not necessarily an API numeric ID. Mark the source used only after at least one publication succeeds.

If saving the database fails after publishing, report the live URL and retry only the record write; never republish to repair bookkeeping. Do not fill analytics from estimates. Review at 24h/7d only when performed or when the user explicitly requests and enables automation.

## Deleted or withdrawn content

A deleted post is withdrawn, not a failed send. Keep history by default. If the user explicitly requests treating it as unpublished in their planning system, return it to draft, clear live publication fields and active approval, and update linked summaries. Do not claim that the real-world publication never occurred. Reuse requires new approval.

## Unsupported capabilities

For each selected platform, report separately: account verified, composer available, media accepted, native scheduling available, API/OAuth connected. Unknown stays unknown. Consult current official requirements before implementing an API. If an action is unsupported, provide a manual handoff; a generic browser session never proves all five platforms work.
